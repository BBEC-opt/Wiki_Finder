# Agent 向 Pi 风格演进计划

## 目标

让 my_wiki 的对话代理逐步具备 Pi agent 的核心特征：小而清晰的 agent loop、可组合的工具、可恢复的会话状态、可扩展的行为，以及用户可理解的执行过程。这里借鉴的是架构原则，不复制 Pi 的终端编码代理或 TypeScript 实现；产品仍以知识库问答、检索和 RAG 为中心。

## 当前范围判断

从仓库目录看，相关实现集中在 `app/services/rag.py`、`app/services/prompts.py`、`app/infrastructure/providers.py`、`app/api/routes.py`、`app/api/schemas.py`，对话行为由 `tests/test_chat.py`、`tests/test_prompts.py`、`tests/test_providers.py` 和 `tests/test_api.py` 覆盖。进入实施前需读这些文件和 `docs/backend-design.md`，确认现有调用链、流式响应格式、持久化状态及工具能力，再更新本节和设计决策。

## 对齐原则

- **核心循环小而显式**：将“组装上下文 → 调用模型 → 执行工具 → 把结果交回模型 → 结束/继续”作为可观察的 agent loop，避免把控制流藏在单个大 RAG 函数里。
- **工具是明确边界**：每个工具声明名称、用途、参数 Schema、执行函数和结果格式；工具输出作为结构化消息进入下一轮，失败也以可理解结果反馈。
- **会话状态可续接**：把用户消息、assistant 回复、工具调用和工具结果按顺序记录，支持多轮上下文与中断恢复；不把所有历史无限塞进提示词。
- **通过扩展点演进**：优先提供 Python 内部注册机制及配置，不在首期引入任意第三方代码加载或动态插件执行。
- **权限最小化**：工具只能做知识库业务必要的事，参数经边界校验；写操作、跨知识库访问及高成本操作要有显式策略。
- **渐进替换**：现有离线默认模型、提供方适配、引用与检索行为保持可用，按能力逐步迁移。

## 分阶段计划

### 阶段 0：现状核对与目标冻结

1. 阅读上述代码、API Schema、数据库模型/迁移、前后端聊天消费逻辑及相关测试。
2. 画出现有对话数据流和 SSE 事件序列，列出当前已支持的工具调用、历史保存、错误处理与模型能力。
3. 明确首期最小范围：单 agent、单轮内可多次工具调用、现有检索能力作为工具或受控 RAG 能力、SSE 兼容策略。
4. 根据核对结果修订本计划，并同步 `docs/backend-design.md`；若前端事件或交互改变，也同步 `docs/frontend-design.md`。

**交付物：** 经代码验证的现状图、API/SSE 兼容决策和数据迁移判断。

### 阶段 1：抽出 Agent Loop 与统一消息模型

1. 在 `app/services/` 建立薄的 agent orchestration 边界；现有检索、回答生成和引用组装继续由其现有职责模块承担。
2. 定义最小消息类型：user、assistant、tool_call、tool_result；为工具调用设置稳定 ID，并保留文本、结构化参数、结果、错误和时间顺序。
3. 建立清晰的终止条件：assistant 最终回复、达到轮数/工具调用上限、超时或取消。
4. 将模型调用能力与工具循环分开，适配现有 provider；明确模型不支持工具调用时的退化路径，保证当前离线提供方仍能完成普通问答。
5. 对关键节点记录安全的追踪信息，不记录密钥或完整敏感文档内容。

**验收：** 现有聊天路径经过 loop 仍能返回相同语义的回答和引用；模型错误、超时、循环上限都有稳定错误处理。

### 阶段 2：工具注册和首批知识库工具

1. 建立轻量 `Tool` 定义与注册表，工具参数使用现有 Pydantic/Schema 能力校验，不新增不必要依赖。
2. 首批只暴露知识库范围内的只读能力，例如检索知识片段、查看文档元信息；不要默认开放 shell、文件系统或任意网络访问。
3. 为检索工具约定参数（知识库范围、查询、数量等）、结果结构（片段、来源、分数/引用标识）及截断策略。
4. 工具执行统一处理参数错误、权限拒绝、无结果、底层异常与超时；错误结果可供模型恢复，但内部异常不泄露给用户。
5. 为工具调用设定最大次数、单次输出上限与总时限，避免无界循环和上下文膨胀。

**验收：** agent 可根据问题决定何时检索；答案引用仍能映射到已有来源；错误与无命中场景有确定行为。

### 阶段 3：会话与可恢复上下文

1. 先审计现有会话/消息存储；若已有合适结构则扩展，避免重复造表。
2. 持久化完整的 agent 事件序列，至少覆盖用户消息、assistant 文本、工具调用和工具结果，并将单次运行与会话关联。
3. 为历史构造单独实现上下文裁剪：保留近期对话和必要工具结果，旧历史通过摘要或选择性回放控制 token 使用。
4. 处理重复提交、请求中断、模型失败和工具失败；明确重试时哪些工具允许重放，避免重复副作用。
5. 若 Schema 改动，提供 Alembic 迁移并记录旧数据兼容策略。

**验收：** 后续轮次能引用必要历史；中断后可解释运行状态；重试不重复执行非幂等动作。

### 阶段 4：流式事件与前端执行呈现

1. 设计稳定的 SSE 事件类型：文本增量、工具开始、工具结果/失败、最终完成、错误（沿用现有事件名可减少破坏性变更）。
2. 给每次运行、消息和工具调用分配可关联 ID；保证事件顺序及终止事件唯一。
3. 前端以简洁状态呈现“正在检索/工具完成/最终回答”，不展示内部提示词或原始异常。
4. 增加断线、取消、加载、空结果和错误状态；核对现有 API 客户端兼容性。
5. 若无法保持旧客户端兼容，提供版本化事件或明确迁移窗口，并更新 API 文档与示例。

**验收：** 普通回复和含工具调用回复均可稳定流式显示；断线与失败状态不会让 UI 永久等待。

### 阶段 5：扩展能力与质量闭环

1. 在核心 loop 稳定后再考虑生命周期钩子（运行前、工具前后、运行完成）和项目内受信任扩展；首期不支持远程插件市场或任意代码加载。
2. 如确有重复业务需求，再开放可配置的工具启停、参数策略和提示词片段；配置需有校验及默认安全值。
3. 建立离线评测样例，覆盖应检索/无需检索、证据不足、错误恢复、多轮追问和工具调用上限。
4. 通过追踪观察模型轮数、工具耗时、失败率、检索命中与上下文大小，依据数据迭代。

**验收：** 扩展不改变核心状态机语义；评测可在不访问网络或付费模型的情况下重复运行。

## 建议模块职责

| 模块 | 职责 |
| --- | --- |
| `app/services/agent.py`（候选） | agent loop、终止条件、运行状态编排 |
| `app/services/tools.py`（候选） | 工具 Schema、注册与统一执行边界；仅在工具增多且职责稳定时拆出 |
| `app/services/retrieval.py` | 继续负责知识检索和结果排序 |
| `app/services/rag.py` | 保留 RAG 领域能力，逐步由 agent loop 调用，不承担通用工具调度 |
| `app/infrastructure/providers.py` | 模型提供方协议适配和能力差异处理 |
| `app/api/routes.py` | 轻薄 API/SSE 接入，不放 agent 业务循环 |

模块名是实施候选，先核对既有结构再决定是否新增，避免为抽象而抽象。

## 兼容性与数据影响

- API/SSE 变更可能影响现有前端和第三方调用方；实施阶段须列明事件字段、顺序和兼容策略。
- 持久化若需记录工具事件或运行状态，需新增迁移；阶段 0 先检查当前消息/会话 Schema，避免重复存储。
- 首期不更换嵌入模型、向量维度或检索索引，不要求重建知识库。
- 默认 provider 必须保留离线可运行路径；不把 Pi 运行时或 TypeScript 包作为依赖。

## 测试与验证清单

- Agent loop：纯文本终止、多次工具调用、最大轮数、取消、模型异常。
- 工具：参数校验、未知工具、成功、无结果、权限拒绝、超时、异常隔离、输出截断。
- 会话：多轮上下文、工具事件回放、裁剪、重复请求和失败后重试。
- API/SSE：事件格式与顺序、最终事件唯一、异常映射、客户端断开。
- 回归：现有 `tests/test_chat.py`、`tests/test_prompts.py`、`tests/test_providers.py`、`tests/test_api.py`，以及受影响的检索/RAG 测试。
- 测试均使用确定性假 provider，不访问网络或付费模型。

## 首期范围建议

优先完成阶段 0 至阶段 2：核实当前链路、抽出可测试的 loop、注册一个只读检索工具并保持引用能力。会话重放、扩展钩子和前端工具状态根据阶段 0 发现及实际产品需要排期，避免首轮同时引入存储、事件协议和插件安全面等多项变化。
