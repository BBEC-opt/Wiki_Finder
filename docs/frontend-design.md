# 前端设计

## 目标与边界

前端是面向单用户演示场景的知识工作台，覆盖知识库管理、资料管理、处理状态查看、检索问答和引用查看。它由 `frontend/index.html`、`frontend/app.js` 和 `frontend/style.css` 组成，与后端同源部署，不使用框架或构建工具。

## 信息架构

```text
知识工作台
├─ 知识库选择
└─ 当前知识库
   ├─ 资料：摄取、处理状态、原文与分块
   ├─ Wiki：处理进度、目录搜索、页面阅读/编辑、来源证据
   └─ 问答：流式回答、引用跳转与会话管理
```

页面保持单页工作台结构，以“资料 / Wiki / 问答”作为一级任务切换。只有出现客户端路由、构建需求或大量可复用组件时，才评估引入前端框架。

## 状态与交互

- 前端状态以 `app.js` 内的单一状态对象为准，DOM 是状态的呈现而不是第二数据源。
- API 请求统一处理成功包与错误包；用户可恢复的错误显示明确操作建议。
- 文档处理状态支持 `pending`、`processing`、`completed`、`failed`，处理中提供可见反馈。
- 问答按 `references → answer → done/error` 消费 SSE；新请求开始时清理上一请求的临时流状态。
- 加载态防止重复提交；空列表、无引用、请求失败分别呈现，不用空白区域代替状态。
- Wiki 使用独立工作区：左侧为页面类型目录和搜索，中间为正文阅读/编辑，右侧为来源证据；可切换到知识关系图谱，图谱根据页面正文中的 `[[slug|标题]]` 内链生成，支持节点拖动、缩放、重新居中及点击进入页面；原文与分块仍使用对话框。
- Wiki 顶部“处理地图”把文档阶段与构建批次合并为 12 步流水线：解析、切分、向量化、索引、候选抽取、引文映射、去重、目录规划、多源合并、持久化、Finalize 和质量检查。节点展示 `pending / running / completed / failed / blocked`，输出优先显示 Chunk、候选、引文、页面与质量问题计数。
- 多资料同时处理时优先展示正在运行的资料，并允许在处理地图中切换；Wiki 视图打开且存在处理中资料时，每 2.5 秒刷新文档、页面与构建详情。完成和失败状态保留，便于验收与排障。
- Wiki 页面支持人工创建和编辑；正文中的 `[[slug|标题]]` 解析为站内页面导航。
- 问答引用优先跳转关联 Wiki 页面，没有关联页时打开来源分块。
- Wiki 页面按受限 Markdown 子集呈现，支持标题、段落、列表、引用、代码块、表格、页码标记和文档内图片；`artifact://<image_id>` 仅映射为页面所属知识记录下的图片 API，不直接读取存储路径或执行原始 HTML。

## 视觉与响应式

- 保持编辑型档案馆的工作台层级，优先突出当前知识库、Wiki 正文与证据来源，不使用占据首屏的营销 Hero。
- 使用 CSS 自定义属性维护颜色、间距和圆角等全局视觉令牌，避免散落重复值。
- 窄屏允许主要区域纵向排列；交互控件需保持可读、可点击，不依赖横向滚动完成核心任务。
- 图标按钮提供可访问名称；键盘可操作弹窗和主要操作；状态不能只通过颜色表达。

## API 依赖

前端只依赖 `/api/v1` 公共契约，不读取后端内部存储路径。接口字段、SSE 事件或错误格式变化时，必须在同一改动中更新前端消费者、测试和本文档。Wiki 阅读器通过知识库页面列表和搜索参数加载目录，通过来源接口展示文档、Chunk 与页码；页面可以没有单一 `knowledge_id`。处理地图组合 `/knowledge/{id}/stages`、`/knowledge/{id}/wiki-builds` 与 `/wiki/builds/{id}`，不根据前端计时猜测阶段状态。

## 设计决策

- 采用原生 HTML/CSS/JavaScript，减少依赖、构建产物与维护成本。
- 前后端同源提供，FastAPI 在 API 路由之后挂载静态站点。
- 当前不引入客户端路由、全局状态库和组件库；只有复杂度出现后再升级。
- “解析原文”和“Wiki 页面”语义分离：原文用于追溯，知识库级页面可以聚合多文档证据并由用户维护。
